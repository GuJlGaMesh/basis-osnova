# Передача результата

Каждое изделие получает ID и ревизию. Изменение паспорта, геометрии, материала, присадки или значимых настроек создаёт новую ревизию. Не перезаписывать единственный проверенный экземпляр.

## Этап 1. Выдача скрипта агентом

Основной результат задачи моделирования — готовый файл `.js` для ручного открытия и запуска человеком в целевой версии БАЗИС. Комплект размещают по [соглашению об артефактах](../architecture/layers.md):

| Артефакт | Обязательное содержание |
|---|---|
| `src/<идентификатор>.js` | Исполняемый скрипт согласованного изделия, с проверкой входных параметров; без псевдокода, скрытых заглушек и несуществующих методов API |
| `brief.md` | Паспорт с подтверждениями и ревизией исходных данных |
| `design.md` | Размерные цепи, конструктивные решения, источники операций API и необходимые материалы/библиотеки |
| `run.md` | Имена файлов комплекта, требования к среде, точка входа, подготовка отдельного документа, ручной запуск, ожидаемый состав результата, сохранение и действия при ошибке |
| `qa.md` | Результаты S0–S3, статус скрипта, непроведённые проверки выполнения и модели, перечень доказательств для следующего этапа |

Если скрипт требует дополнительные файлы, перечислить и приложить их либо указать подтверждённую установленную библиотеку. Не оставлять путь к файлу на компьютере агента как рабочую зависимость на компьютере оператора. Инструкция должна позволять перенести комплект и определить, какой `.js` запускать.

Порядок: проверить паспорт и расчёт → подготовить скрипт и инструкцию → проверить S0–S2 → записать ревизии и контрольную сумму итогового `.js` → закрыть S3 по [quality gates](quality-gates.md) → передать комплект. При изменении скрипта после проверки обновить хеш и затронутые результаты. Отсутствие локального БАЗИС не блокирует этот этап. Если подготовительные критерии не закрыты, указать конкретный блокер; не называть незавершённый код готовым скриптом.

При выполненных S0–S3 и отсутствии запуска указать: «Скрипт готов к ручному запуску; запуск и модель в БАЗИС не проверены». Готовность скрипта и модели фиксировать раздельно по каноническим статусам в [quality gates](quality-gates.md).

## Этап 2. Проверка и сохранение человеком

Оператор вручную открывает и запускает скрипт по `run.md`, выполняет [процесс БАЗИС](bazis.md), сохраняет нативную модель средствами приложения и открывает её заново. Файл модели `.b3d`, деталировка и экспорты появляются на этом этапе; их наличие не является условием выдачи подготовленного скрипта.

Порядок: выполнить скрипт → проверить результат по применимым G0–G8 → сохранить файл → открыть заново и завершить проверки → сформировать экспорты из проверенной ревизии → сверить позиции, количество и размеры → записать контрольную сумму → дополнить комплект доказательствами и статусом модели.

Оператор возвращает ревизию и хеш запущенного скрипта, профиль среды, журнал или полный текст ошибки, нативный файл, измерения и требуемые ведомости. Агент обновляет `qa.md` только по полученным доказательствам. Скриншот успешного запуска не закрывает проверки размеров, кромок, присадки и сохранения.

Расширение нативной модели не подменяют переименованием другого формата. Производственный комплект и применимость экспортов определяет принимающий технолог; для эскиза сокращение состава записывают явно, файлы ЧПУ требуют отдельного допуска.

Контрольную сумму можно получить в PowerShell командой `Get-FileHash -Algorithm SHA256 -LiteralPath 'путь-к-реальному-файлу'`, подставив существующий путь. Хеш связывает доказательства с файлом, но не доказывает качество геометрии.

Если запуск завершился ошибкой или результаты проверки не переданы, статус модели не повышают. Исправленный скрипт получает новую ревизию; ранее полученные доказательства применимы только в явно обоснованной части.
