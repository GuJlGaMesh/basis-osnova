# Работа в БАЗИС-Мебельщике

## Подготовка среды

1. Записать в паспорт версию и сборку приложения, способ работы, версии библиотек и доступные модули.
2. Проверить доступность материалов и фурнитуры из паспорта. Отсутствующий артикул не заменять похожим без согласования.
3. Сохранить исходную модель и работать в копии либо отдельном документе. Зафиксировать путь результата и действующие настройки размеров/кромок.
4. Сверить операции с [официальными источниками](../architecture/dependencies.md) и локальной справкой. Составить в `design.md` таблицу: операция → имя метода или команда интерфейса → источник/раздел → версия → результат проверки.
5. Для скриптов сначала провести минимальный эксперимент в отдельном файле: создать панель, назначить нужный материал, проверить размер и оси, сохранить и открыть заново. Если задача включает кромки или отверстия, проверить по одной соответствующей операции отдельно.

## Скрипты

Исполнять CAD-операции в среде БАЗИС. Наличие JavaScript не означает наличие Node.js, DOM, npm-пакетов или произвольного доступа к файловой системе. Синтаксис и возможности проверять на целевом движке.

Разделять проверку входных данных, расчёт деталей, адаптер API и сбор фактических результатов. Выполнять валидацию до первой мутации. Не смешивать примеры разных поколений API: официальная страница примеров описывает API 5, но совместимость с установленной сборкой требует проверки. Смена режима API — отдельное решение, а не универсальный способ устранить ошибку.

Документировать поведение повторного запуска: либо создавать новый самостоятельный экземпляр, либо обновлять только принадлежащую генератору группу по стабильному ID. Повторный запуск не должен незаметно удваивать детали или менять чужую модель. Имена деталей для пользователя не заменяют стабильные ID.

Подготовить обработку отмены пользователем и ошибки в середине построения. Использовать историю/откат только если механизм подтверждён на целевой версии; иначе работать с отдельным файлом и не выдавать частичный результат за завершённый. Не очищать всю модель или историю ради удобства генератора.

При загрузке другого файла учитывать возможность замены текущей модели: этот риск прямо описан в официальных примерах операций ввода-вывода. До такой операции сохранить пользовательский документ.

Лог должен связывать запуск с ревизией паспорта и исходников, параметрами, созданными ID, исключениями и путём результата. После построения измерить объекты модели независимо от таблицы рассчитанных координат.

## Работа через интерфейс

Зафиксировать активный документ, выделение, текущие материалы и систему координат. Использовать точный числовой ввод, где он доступен; положение курсора не доказывает размер. После создания каждой группы проверить панель свойств, размер, ориентацию и принадлежность сборке.

Если команда или интерфейс отличаются от инструкции, сверить справку установленной версии. Не выполнять слепую цепочку кликов по предполагаемым координатам. Если доступного инструмента управления приложением нет, подготовить точные действия для оператора и оставить проверки запуска незавершёнными.

## Последовательность построения

Согласованный паспорт → расчёт и схема соединений → корпус → перегородки и полки → задник и опоры → фасады и ящики → материалы и кромки → фурнитура и присадка → позиции и деталировка → сохранение и повторное открытие → [quality gates](quality-gates.md).

Порядок отдельных операций можно менять по требованиям API или соединения, записав причину. Проверки после сохранения пропускать нельзя.
