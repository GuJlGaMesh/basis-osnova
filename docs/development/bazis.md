# Работа в БАЗИС-Мебельщике

## Подготовка скрипта агентом

1. Взять подтверждённую версию приложения из раздела Tech Stack в [README.md](../../README.md) и перенести в паспорт без повторного вопроса. Записать известную сборку, профиль API, версии библиотек и доступные модули; уточнять недостающие сведения, от которых зависят операции скрипта.
2. Подтвердить материал, фурнитуру и источники библиотек из паспорта либо реализовать обязательный выбор и проверку совместимости до построения при ручном запуске. Отсутствующий артикул не заменять похожим без согласования. Для проверки доступности в установленной среде подготовить конкретные действия оператора.
3. Сверить операции с [официальными источниками](../architecture/dependencies.md) и справкой целевой версии. Составить в `design.md` таблицу: операция → имя метода → источник/раздел → применимый профиль API → подтверждение по документации → результат выполнения или «не запускалось». Документальное подтверждение метода и проверка его выполнения — разные доказательства.
4. Подготовить готовый `.js`, независимый расчёт и `run.md` по [правилам передачи](releases.md). Перед выдачей выполнить S0–S3 из [quality gates](quality-gates.md). Неподтверждённый метод не заменять правдоподобным именем или заглушкой.

БАЗИС на компьютере агента не требуется: скрипт запускает человек либо агент при доступном управлении и разрешении пользователя. Отсутствие управления окном не является причиной заменить скрипт общими советами или остановить независимую подготовку. Отчёт о запуске и фактической модели до получения доказательств остаётся незавершённым.

## Скрипты

CAD-операции исполняются в среде БАЗИС при запуске человеком или агентом. Наличие JavaScript не означает наличие Node.js, DOM, npm-пакетов или произвольного доступа к файловой системе. Выбирать синтаксис по документации целевого движка; проверку его выполнения фиксировать отдельно. Проверка синтаксиса сторонним JavaScript-движком подтверждает только то, что этот движок смог разобрать исходник.

Разделять проверку входных данных, расчёт деталей, адаптер API и сбор фактических результатов. Выполнять валидацию до первой мутации. Не смешивать примеры разных поколений API: версия приложения не определяет автоматически применимость опубликованного примера. Смена режима API — отдельное решение, а не универсальный способ устранить ошибку.

Выдавать исполняемый файл с понятной точкой входа, единицами и параметрами, а не только фрагмент кода в сообщении. Зависимости и способ их размещения на компьютере оператора перечислять явно. Локальные пути агента, псевдокод и незавершённые обязательные операции недопустимы в скрипте, отмеченном готовым к ручному запуску.

## Очистка текущей модели перед построением

Штатный режим каждого скрипта — полная замена содержимого текущей модели. После успешного ввода и проверки параметров скрипт сам удаляет все прежние объекты текущей модели, включая скрытые и вложенные, и затем строит изделие заново. Сохранение только «своей» группы и добавление ещё одного экземпляра не являются режимами по умолчанию.

Не требовать от человека заранее пустой документ, ручное удаление деталей или повторное разрешение на штатную очистку. Запретить блокирующую проверку с сообщением «откройте пустую модель», в том числе основанную лишь на общем счётчике элементов: служебный контейнер не равен пользовательской геометрии. Пустая текущая модель — нормальный случай: очистка ничего не удаляет и построение продолжается. Отсутствие активного документа отличать от пустого документа и обрабатывать отдельно средствами подтверждённого API.

Последовательность: проверить наличие целевого документа, входы и доступные зависимости → очистить текущую модель → убедиться, что старые объекты удалены → создать изделие. Использовать документированный для целевой версии механизм очистки; не угадывать имя метода, не удалять сам служебный контейнер документа. Если очистка не удалась, завершить запуск с конкретной ошибкой до создания новых деталей; не продолжать поверх старого содержимого.

Повторный запуск с теми же параметрами должен оставлять одно изделие с тем же составом и геометрией; прежние ручные правки в текущей модели тоже заменяются. Очистка ограничена содержимым активной модели: не закрывать и не очищать другие документы, не удалять файлы с диска, материалы из базы или библиотечные файлы. Сохранение `.b3d` выполняют средствами БАЗИС; агент может сохранить и повторно открыть отдельную рабочую копию в рамках разрешённого запуска.

Подготовить обработку отмены пользователем и ошибки в середине построения. Отмена ввода или неверные параметры до очистки оставляют модель без изменений. После очистки не обещать восстановление прежних объектов, если откат не подтверждён на целевой версии. При сбое обозначить незавершённый результат; следующий корректный запуск снова очищает модель перед построением. Очистка объектов не означает необходимость отдельно стирать историю документа.

При загрузке другого файла учитывать возможность замены текущей модели: этот риск прямо описан в официальных примерах операций ввода-вывода. До такой операции сохранить пользовательский документ.

Лог должен связывать запуск с ревизией паспорта и исходников, параметрами, созданными ID, исключениями и путём результата. Способ записи лога выбирать из подтверждённых возможностей API; при их отсутствии оператор сохраняет сообщения и сведения о запуске вручную. План независимого измерения объектов модели после построения включать в `run.md`.

## Открытие и запуск

Оператор (человек или агент) выполняет следующие действия на компьютере с БАЗИС:

1. Перенести комплект, сверить имя и ревизию запускаемого `.js`, требования к API, наличие материалов и библиотек из `run.md`.
2. Выбрать текущий документ, содержимое которого будет полностью заменено; нужный прежний результат сохранить до запуска. Ручная очистка и создание нового пустого документа не требуются. Зафиксировать единицы, систему координат и настройки кромок.
3. Через штатный механизм скриптов установленной версии открыть переданный `.js`. Конкретные названия команд брать из справки этой версии; не придумывать пункты меню и сочетания клавиш.
4. Если использованные операции ещё не проверялись в этом профиле среды, сначала выполнить подготовленный минимальный эксперимент в отдельном документе: панель, материал, размеры и оси, сохранение и повторное открытие. Кромки и отверстия проверять отдельными операциями, если они требуются изделию. При несовместимости остановиться и передать полный текст ошибки.
5. Запустить скрипт изделия: после проверки ввода он сам очищает текущую модель и строит новое изделие. Проверить сообщения и ожидаемый состав результата. Успешное выполнение не означает прохождение геометрических и технологических проверок.
6. По `run.md` измерить фактические объекты независимо от таблицы координат генератора, сохранить модель средствами БАЗИС, повторно открыть и завершить применимые G0–G8.
7. Вернуть файл и доказательства по [правилам передачи](releases.md). При ошибке приложить текст, строку/операцию, ревизию скрипта и профиль среды; частичный результат не получает успешный статус.

Если интерфейс отличается от инструкции, сверить справку установленной версии. Ручные исправления размеров и свойств требуют точного числового ввода и повторной проверки; положение курсора и внешний вид не доказывают размер. Факт ручного изменения модели нужно записать: оно может устранить ошибку экземпляра, но не подтверждает исправление скрипта.

## Последовательность построения

Скрипт реализует согласованную схему: проверка входов → очистка текущей модели → корпус → перегородки и полки → задник и опоры → фасады и ящики → материалы и кромки → фурнитура и присадка → позиции. Для встроенной техники учитывать отдельные требования из [правил конструирования](modeling.md). После запуска оператор проверяет модель, формирует деталировку, сохраняет и повторно открывает файл по [quality gates](quality-gates.md).

Порядок отдельных операций можно менять по требованиям API или соединения, записав причину. Проверки после сохранения пропускать нельзя.
