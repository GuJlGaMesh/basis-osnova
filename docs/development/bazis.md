# Работа в БАЗИС-Мебельщике

## Подготовка скрипта агентом

1. Взять подтверждённую версию приложения из раздела Tech Stack в [README.md](../../README.md) и перенести в паспорт без повторного вопроса. Записать известную сборку, профиль API, версии библиотек и доступные модули; уточнять недостающие сведения, от которых зависят операции скрипта.
2. Подтвердить материал, фурнитуру и источники библиотек из паспорта либо реализовать обязательный выбор и проверку совместимости до построения при ручном запуске. Отсутствующий артикул не заменять похожим без согласования. Для проверки доступности в установленной среде подготовить конкретные действия оператора.
3. Сверить операции с [официальными источниками](../architecture/dependencies.md) и справкой целевой версии. Составить в `design.md` таблицу: операция → имя метода → источник/раздел → применимый профиль API → подтверждение по документации → результат выполнения или «не запускалось». Документальное подтверждение метода и проверка его выполнения — разные доказательства.
4. Подготовить готовый `.js`, независимый расчёт и `run.md` по [правилам передачи](releases.md). Перед выдачей выполнить S0–S3 из [quality gates](quality-gates.md). Неподтверждённый метод не заменять правдоподобным именем или заглушкой.

БАЗИС на компьютере агента не требуется: штатный порядок — подготовка скрипта здесь и ручное открытие и выполнение человеком на компьютере с БАЗИС. Отсутствие управления окном не является причиной заменить скрипт общими советами или остановить независимую подготовку. Отчёт о запуске и фактической модели до получения доказательств остаётся незавершённым.

## Скрипты

CAD-операции исполняются в среде БАЗИС при ручном запуске человеком. Наличие JavaScript не означает наличие Node.js, DOM, npm-пакетов или произвольного доступа к файловой системе. Выбирать синтаксис по документации целевого движка; проверку его выполнения фиксировать отдельно. Проверка синтаксиса сторонним JavaScript-движком подтверждает только то, что этот движок смог разобрать исходник.

Разделять проверку входных данных, расчёт деталей, адаптер API и сбор фактических результатов. Выполнять валидацию до первой мутации. Не смешивать примеры разных поколений API: версия приложения не определяет автоматически применимость опубликованного примера. Смена режима API — отдельное решение, а не универсальный способ устранить ошибку.

Выдавать исполняемый файл с понятной точкой входа, единицами и параметрами, а не только фрагмент кода в сообщении. Зависимости и способ их размещения на компьютере оператора перечислять явно. Локальные пути агента, псевдокод и незавершённые обязательные операции недопустимы в скрипте, отмеченном готовым к ручному запуску.

Документировать поведение повторного запуска: либо создавать новый самостоятельный экземпляр, либо обновлять только принадлежащую генератору группу по стабильному ID. Повторный запуск не должен незаметно удваивать детали или менять чужую модель. Имена деталей для пользователя не заменяют стабильные ID.

Подготовить обработку отмены пользователем и ошибки в середине построения. Использовать историю/откат только если механизм подтверждён на целевой версии; иначе работать с отдельным файлом и не выдавать частичный результат за завершённый. Не очищать всю модель или историю ради удобства генератора.

При загрузке другого файла учитывать возможность замены текущей модели: этот риск прямо описан в официальных примерах операций ввода-вывода. До такой операции сохранить пользовательский документ.

Лог должен связывать запуск с ревизией паспорта и исходников, параметрами, созданными ID, исключениями и путём результата. Способ записи лога выбирать из подтверждённых возможностей API; при их отсутствии оператор сохраняет сообщения и сведения о запуске вручную. План независимого измерения объектов модели после построения включать в `run.md`.

## Ручное открытие и запуск человеком

Оператор выполняет следующие действия на компьютере с БАЗИС:

1. Перенести комплект, сверить имя и ревизию запускаемого `.js`, требования к API, наличие материалов и библиотек из `run.md`.
2. Сохранить рабочий пользовательский документ; для первого запуска открыть отдельный документ или копию. Зафиксировать активный документ, выделение, единицы, систему координат и настройки кромок.
3. Через штатный механизм скриптов установленной версии вручную открыть переданный `.js`. Конкретные названия команд брать из справки этой версии; не придумывать пункты меню и сочетания клавиш.
4. Если использованные операции ещё не проверялись в этом профиле среды, сначала выполнить подготовленный минимальный эксперимент в отдельном документе: панель, материал, размеры и оси, сохранение и повторное открытие. Кромки и отверстия проверять отдельными операциями, если они требуются изделию. При несовместимости остановиться и передать полный текст ошибки.
5. Вручную запустить скрипт изделия, проверить сообщения и ожидаемый состав результата. Успешное выполнение не означает прохождение геометрических и технологических проверок.
6. По `run.md` измерить фактические объекты независимо от таблицы координат генератора, сохранить модель средствами БАЗИС, повторно открыть и завершить применимые G0–G8.
7. Вернуть файл и доказательства по [правилам передачи](releases.md). При ошибке приложить текст, строку/операцию, ревизию скрипта и профиль среды; частичный результат не получает успешный статус.

Если интерфейс отличается от инструкции, сверить справку установленной версии. Ручные исправления размеров и свойств требуют точного числового ввода и повторной проверки; положение курсора и внешний вид не доказывают размер. Факт ручного изменения модели нужно записать: оно может устранить ошибку экземпляра, но не подтверждает исправление скрипта.

## Последовательность построения

Скрипт реализует согласованную схему: корпус → перегородки и полки → задник и опоры → фасады и ящики → материалы и кромки → фурнитура и присадка → позиции. Для встроенной техники учитывать отдельные требования из [правил конструирования](modeling.md). После ручного запуска оператор проверяет модель, формирует деталировку, сохраняет и повторно открывает файл по [quality gates](quality-gates.md).

Порядок отдельных операций можно менять по требованиям API или соединения, записав причину. Проверки после сохранения пропускать нельзя.
