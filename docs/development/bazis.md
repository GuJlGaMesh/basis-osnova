# Работа в БАЗИС-Мебельщике

## Маршрут подготовки

Входы и критерии результата определяет [гейт скрипта](gates/script.md), конструкцию — [карточка мебели](furniture/README.md). Здесь описаны устройство генератора, работа со сценой и повторно используемые операции. Состав файлов — в [контракте выпуска](releases.md), версия среды — в [README](../../README.md#tech-stack).

## Скрипты

CAD-операции исполняются в среде БАЗИС при запуске человеком или агентом. Наличие JavaScript не означает наличие Node.js, DOM, npm-пакетов или произвольного доступа к файловой системе. Выбирать синтаксис по документации целевого движка; проверку его выполнения фиксировать отдельно. Проверка синтаксиса сторонним JavaScript-движком подтверждает только то, что этот движок смог разобрать исходник.

Разделять получение параметров, проверку входных данных, расчёт деталей и соединений, адаптер API и сбор фактических результатов. Форма и пакетный запуск передают расчёту обычные значения; расчёт не зависит от элементов интерфейса и не меняет сцену. Выполнять валидацию до первой мутации. Не смешивать примеры разных поколений API: версия приложения не определяет автоматически применимость опубликованного примера. Смена режима API — отдельное решение, а не универсальный способ устранить ошибку.

Декларации типов помогают проверять имена и сигнатуры, но не подтверждают выполнение метода в установленной сборке. Совпадающие копии деклараций не являются независимыми доказательствами. Новый механизм сначала проверять минимальным примером в целевой среде по [сценарию изменения API](../change-scenarios/api-change.md).

Для обязательных операций вести в `design.md` таблицу: назначение → имя метода и сигнатура → источник/раздел → применимый профиль API → документальное подтверждение → результат выполнения либо «не запускалось». Источник и фактический запуск записываются отдельно; таблица служит доказательством S1, а не заменой проверки в БАЗИС.

Выдавать исполняемый файл с понятной точкой входа, единицами и параметрами, а не только фрагмент кода в сообщении. Зависимости и способ их размещения на компьютере оператора перечислять явно. Локальные пути агента, псевдокод и незавершённые обязательные операции недопустимы в скрипте, отмеченном готовым к ручному запуску.

## Параметры и повторное редактирование

При нескольких связанных настройках использовать форму с группами габаритов, материалов, конструкции и крепежа. Обязательные неизвестные параметры сохраняют обязательный ввод. Для подтверждённого профиля API элементы `Action.Properties` позволяют выбирать числа, материалы, кромки и фурнитуру; зависимые поля включают только для выбранного исполнения.

Для набора секций разделять общие настройки и страницы отдельных модулей. Показывать ID и тип текущего модуля, обеспечивать прямой переход к нему и связь с блоком в сцене. Поля страницы зависят от типа модуля; неприменимый параметр отключать с пояснением либо скрывать, а не молча игнорировать его значение. Общие значения и локальные переопределения различать явно; смена общей настройки не должна незаметно стирать переопределение. При смене типа секции несовместимые параметры сбрасывать явно и повторно проверять входы. Правила расположения и зависимостей — в [компоновке модулей](furniture/kitchen.md).

Отделять настройки отображения от состава изделия. Команда скрытия фасадов или изоляции модуля помогает осмотру, но не исключает детали из ведомости и не меняет параметры конструкции. Отсутствие фасадов в проектируемом изделии задаётся отдельным параметром состава. Служебную окраску кромок и упрощённые габариты техники отличать от фактического материала и изготовляемых деталей.

Сохранённые настройки содержат идентификатор типа изделия и версию схемы параметров. После загрузки повторно проверять значения и доступность библиотек; старый файл настроек не подтверждает их пригодность для новой ревизии. Сохранять пользовательские параметры, а не ссылки на объекты открытой модели или вычисленные размеры, которые могут устареть.

Различать параметрическое перестроение и нативную эластичность. Параметрический блок организует повторное выполнение логики построения; связка `BeginParametricBlock` / `EndParametricBlock` и обработчики изменения параметров применяются после проверки их жизненного цикла в целевой среде. `ElasticResize` использует уже заложенные ограничения нативной сборки и не создаёт их для произвольного фрагмента. Конструктивные ограничения описаны в [правилах эластичности](modeling.md#эластичное-изменение-размера).

Для предварительного просмотра учитывать собственные созданные объекты и границы текущего действия. Вызов `DeleteNewObjects()` допустим только при подтверждённой области удаления; перенос объекта к другому владельцу требует повторной проверки этого поведения. Подтверждение фиксирует результат, отмена восстанавливает предыдущее состояние. Редактирование существующего экземпляра — отдельный явно выбранный режим; обычный запуск остаётся добавлением нового изделия.

## Повторно используемые операции

Общую часть генераторов делить по ответственности: параметры, геометрические расчёты, построение панелей, работа со сборками, установка крепежа и диагностика. Для каждого переиспользуемого приёма фиксировать входы и единицы, зависимости, область изменения модели и критерий проверки. Реализацию подключения модулей выбирать по подтверждённому режиму API; наличие `require` или `system.include` не означает совместимости с произвольным npm-пакетом. При необходимости собирать общие исходные части в один выдаваемый `.js` по [правилам выпуска](releases.md).

Обход дерева для чтения отделять от обхода с изменением коллекции. Порядок обработки родителя и потомков задавать явно; при удалении или переносе элементов использовать снимок коллекции либо подходящий обратный обход. Смена `Owner` должна сохранять мировые положение и ориентацию, в том числе у вложенного объекта с повёрнутым родителем. Служебные рамки не считать изготовляемыми деталями. Пустую оболочку удалять после проверки перенесённых объектов.

Библиотечный узел описывать файлом, артикулом, ревизией или хешем, допустимыми параметрами и способом установки. После создания проверять фактический результат, а после эластичного изменения — полученные размеры и сохранность связей. Отсутствующий или несовместимый узел не заменять похожим. Схему соединения выбирать по [правилам моделирования](modeling.md#соединения-и-движение).

Контракт установки библиотечного фрагмента включает единицы, локальную точку привязки, направления осей, сторону и целевую монтажную базу. Разные точки привязки нормализовать в адаптере явным преобразованием и проверять по контрольным точкам. Не рассчитывать на ручное перемещение фрагмента после каждого штатного запуска. Геометрически похожий фрагмент с другой базой или монтажной схемой не считается взаимозаменяемым.

## Пакетная обработка

Пакетный запуск работает по фиксированному списку входов и сохраняет результаты в отдельную выходную папку. Не включать её в последующий поиск входных файлов, не перезаписывать исходники и не допускать совпадения выходных имён. До загрузки следующей модели учитывать несохранённый документ; рабочие копии и правила сохранения описаны ниже.

Для каждого входа записывать параметры, стадию выполнения, результат и путь выходного файла. Продолжать после ошибки отдельного изделия только при подтверждённой очистке собственного результата и восстановлении рабочего состояния. Выгрузка отдельных объектов не должна временно удалять остальные объекты рабочего документа в расчёте на последующую отмену: использовать отдельную копию. Формат результатов и диагностические ограничения — в [проверках](testing.md#диагностика-деталей-и-связей).

## Добавление в текущую сцену

По умолчанию скрипт дополняет текущую модель новым отдельным блоком. Существующие объекты, их вложенность, свойства и расположение сохраняются. Повторный запуск добавляет ещё один экземпляр; не обновляет и не удаляет прежний. Полная замена возможна только по отдельному явному запросу пользователя.

Проверить входы и зависимость до создания блока. Для связанной нативной сборки использовать проверенный порядок импорта из [model-to-script.md](model-to-script.md#импорт-связанной-нативной-сборки). Одного назначения Owner=Model после Block.Load недостаточно: геометрия может быть доступна, а выделение через интерфейс — вызывать сбой. Не использовать загрузку вместо текущего документа для вставки.

Выравнивать вставляемые модули по передней плоскости фасадов; разница глубины располагается сзади. Для прямого ряда по глобальной X определять лицевую плоскость по панелям с нормалью вдоль Z, исключая выступающие ручки и служебные рамки. Повернутые ряды и разные фасадные плоскости требуют явной базы, а не предположения по габариту документа. По умолчанию ставить вплотную боковинами, без дополнительного зазора; иной зазор только по явному требованию. Место вставки описывать в паспорте.

При отмене или неверном вводе сцена остаётся неизменной. При сбое можно удалить только контейнер, созданный текущим запуском; нельзя чистить прежнюю модель. Пустая сцена также поддерживается, но не требуется. Служебная рамка не равна физическому изделию и не используется как база выравнивания.

Журнал содержит ревизию, параметры и этап. Проверять неизменность ранее существовавших объектов, положение нового блока, повторную вставку и сохранение. Подробности — [testing.md](testing.md).

## Открытие и запуск

Оператор (человек или агент) выполняет следующие действия на компьютере с БАЗИС:

1. Перенести комплект, сверить имя и ревизию запускаемого `.js`, требования к API, наличие материалов и библиотек из `run.md`.
2. Выбрать текущий документ для добавления модуля; сохранить рабочее состояние. Очистка и пустой документ не требуются. Зафиксировать единицы, систему координат и настройки кромок.
3. Через штатный механизм скриптов установленной версии открыть переданный `.js`. Конкретные названия команд брать из справки этой версии; не придумывать пункты меню и сочетания клавиш.
4. Если использованные операции ещё не проверялись в этом профиле среды, сначала выполнить подготовленный минимальный эксперимент в отдельном документе: панель, материал, размеры и оси, сохранение и повторное открытие. Кромки и отверстия проверять отдельными операциями, если они требуются изделию. При несовместимости остановиться и передать полный текст ошибки.
5. Запустить скрипт изделия: после проверки ввода он добавляет новое изделие, сохраняя прежние объекты. Проверить сообщения и ожидаемый состав результата. Успешное выполнение не означает прохождение геометрических и технологических проверок.
6. По `run.md` измерить фактические объекты независимо от таблицы координат генератора, сохранить модель средствами БАЗИС, повторно открыть и завершить применимые G0–G8.
7. Вернуть файл и доказательства по [правилам передачи](releases.md). При ошибке приложить текст, строку/операцию, ревизию скрипта и профиль среды; частичный результат не получает успешный статус.

Если интерфейс отличается от инструкции, сверить справку установленной версии. Ручные исправления размеров и свойств требуют точного числового ввода и повторной проверки; положение курсора и внешний вид не доказывают размер. Факт ручного изменения модели нужно записать: оно может устранить ошибку экземпляра, но не подтверждает исправление скрипта.

## Последовательность построения

Скрипт реализует согласованную схему: проверка входов → новый контейнер → корпус → перегородки и полки → задник и опоры → фасады и ящики → материалы и кромки → фурнитура и присадка → позиции. Для встроенной техники учитывать отдельные требования из [правил конструирования](modeling.md). После запуска оператор проверяет модель, формирует деталировку, сохраняет и повторно открывает файл по [quality gates](quality-gates.md).

Порядок отдельных операций можно менять по требованиям API или соединения, записав причину. Проверки после сохранения пропускать нельзя.

## Самостоятельный запуск

Готовый генератор работает внутри БАЗИС без ИИ и подключения к сервису агента. Параметры и нативные зависимости поставляются вместе со скриптом. Проверки разработки не включать в обычный пользовательский запуск: достаточно проверки ввода, зависимостей и результата построения. Пакетный вызов функции генератора может передавать размеры напрямую; интерактивная точка входа запрашивает их у пользователя.
